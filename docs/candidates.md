# Candidate definitions and reconstruction

The catalog contains **122 distinct codes**: 18 with reported distance 12,
96 with reported distance 14, and 8 with reported distance 16. There are 104
definitions with `q=3` and 18 with `q=4`. This is the consolidated candidate
catalog, rather than a record of every intermediate search result.

Each JSON definition in `src/armillary/data/candidates/` specifies the code
without a search program or a precomputed matrix. `data/catalog.json` supplies
dimensions, reported distance bounds, the matrix hash, and a SHA-256 checksum
of each definition file.

| Field | Meaning |
| --- | --- |
| `p` | Cyclic lift period, distinct from the physical error probability |
| `q` | Number of lanes, either 3 or 4 |
| `n`, `k` | Data-qubit count and logical-qubit count; `n = 12*q*p` |
| `mode` | `common` uses one displacement per group and odd layer; `channel` uses one per lane |
| `skeleton.xrows`, `skeleton.zrows` | Ordered retained X- and Z-check groups |
| `top` | Lane permutations at the even transport layers |
| `phases` | Integer displacements at the odd transport layers, taken modulo `p` |
| `matrix_sha256` | Identity of the ordered reconstructed X/Z matrices |
| `exact_distance`, `distance_lower`, `distance_upper` | Reported distances from the consolidated catalog |

The full IDs are stable matrix identifiers. The three codes highlighted in
the decoding examples also have short aliases:

| Alias | Full ID | Parameters |
| --- | --- | --- |
| `8749` | `P-2b28b13c8749` | `[[3636,1822,12]]` |
| `9053` | `P-54f8f55d9053` | `[[4932,2470,14]]` |
| `p181` | `P-0bc3b705dfd0` | `[[8688,4348,16]]` |

## Physical replay

`load_candidate()` follows all twelve transport layers in fixed physical
slots. All ancilla groups take part in swaps, including removed check groups.
Retained groups additionally apply their X- or Z-check CNOTs. Propagating
binary basis labels through these operations verifies the intended parity
checks and absence of unwanted residual CNOT coupling. The reverse sweep
must recover the same ordered check supports and restore every role label
to its initial slot.

The resulting `H_X` and `H_Z` are represented by lists of Python integers:
bit `j` denotes column `j`. Exact binary elimination reconstructs the ranks
and checks `k = n - rank(H_X) - rank(H_Z)`. The matrix hash is SHA-256 of the
UTF-8 serialization

```python
json.dumps([n, list(map(hex, hx)), list(map(hex, hz))], separators=(",", ":"))
```

This convention includes row order, so reordering checks changes the hash
even when it leaves the abstract code unchanged.

```python
from armillary.candidates import list_candidates, load_candidate
from armillary.algebra import indices

catalog = list_candidates()        # metadata only
code = load_candidate("8749")      # physical replay and identity checks
first_x_support = indices(code["_hx"][0])
```

Reconstruction checks the supplied definitions, dimensions, transport, and
matrix identity. It does **not** rerun minimum-distance certification or
geometric routing optimization. The distance columns describe the reported
catalog values, not new distance certificates generated by this package.

## Hardware layouts of the representative codes

The discrete `top` and `phases` parameters determine circuit pairings. They do not specify continuous wire paths or their placement on routing faces. The separate [hardware-layout module](../hardware_layouts/) supplies those data for the three representative codes, together with geometry and HAL-metric verification. Each layout is bound to the corresponding catalog candidate through its ordered matrix SHA-256. The other 119 catalog entries have no released continuous hardware layout in this module.
